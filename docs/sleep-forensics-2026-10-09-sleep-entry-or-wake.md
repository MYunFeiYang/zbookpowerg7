# 取证：到底是「没睡着」还是「没法唤醒」？（2026-10-09 19:1x）

**触发问题**：用户问「到底是没睡着还是没法唤醒？」

---

## 结论先行

**两个说法都不完全对，精确答案是三态中的第三态：**

> **睡眠流程被完整「发起」并按序走到了 OS 侧交接的最后一步，然后就彻底断了——此后既没有「睡成了」的证据，也没有「醒过来」的证据。**
> 也就是**卡在「睡眠转换」这一段**，而不是「睡眠请求被拒」那一种「没睡着」。

- ❌ **不是**「请求被拒 / 根本没进睡眠流程」——那样会立刻回醒并在日志里留下 aborted-sleep + 继续运行。
- ❌ **不是**「睡进去了、只是黑屏没醒」——那样 23 秒后的定时唤醒（RTC/平台层）会把它拉起来，日志里会出现 `DarkWake`。
- ✅ **是** 入睡侧交接完成后，整个系统**静默**，直到被硬断电。

**但必须诚实标注边界**：OS 日志**无法**区分下面两种物理实况，二者在软件层同形：

| 假设 | 物理实况 | OC-Little 官方定性 |
|---|---|---|
| **A** | 平台根本没进入 S0ix，CPU 卡在入睡交接里空转 | 「机器一直停滞在睡眠过程，**始终没有睡眠成功**」 |
| **B** | 确实进了 S0ix，但唤醒源（电源键/EC/RTC）一个都没送达到 CPU | 「睡眠后无法被唤醒」 |

⇒ 要切开 A / B，**只能靠物理量**（温度/风扇/功耗），见文末判据与实验。

## 一、硬证据（全部来自 `pmset -g log`，自洽可信）

| # | 证据 | 实测值 | 能证明什么 |
|---|---|---|---|
| 1 | `Entering Sleep state` 次数 | **7** | 2 天内每一次睡眠请求**都被受理并走进入睡流程** |
| 2 | `Wake from …` 次数 | **0** | 一次都没醒过（100% 失败，非偶发） |
| 3 | `DarkWake` 次数 | **0** | 连「暗唤醒」都没发生过 |
| 4 | 入睡瞬间最后一条日志 | `PM Client Acks Delays to Sleep notifications: [bluetooth.sleep slow(519ms)] [apsd slow(1094ms)]` @18:03:15 | **OS 侧通知扇出完整跑完** ⇒ 不是「没进流程」，是**交棒给了平台层** |
| 5 | 交棒之后 | 日志**完全静默**，直到断电 | 系统停止执行 |
| 6 | 预约唤醒是否兑现 | 12:03:16 入睡，预约 **23 秒**后的 `GaugingMitigationActions` 唤醒 → **34 分钟内未触发** | 平台层连 RTC 闹钟都没兑现 |
| 7 | panic 报告 | **无**（`DiagnosticReports/*panic*` 无匹配） | 不是崩溃，是**静默冻住** |
| 8 | 硬断电前旧 boot 有无日志 | 18:06:35–18:06:50 **只有开机日志**（apfs trim / launchd hello / boot-args ），旧 boot 零输出 | 断电时系统**已完全停止执行**，连软关机流程都没跑 ⇒ 是真·硬关机 |

**SMC shutdown cause 全部是 `5: Software initiated shutdown` —— 这是 VirtualSMC 的默认/假值，不具区分度**（正常重启也报 5），不能据此认为机器是「软关机」。

### 关键修正：`log show` 之前查不到日志是「命令被遮蔽」，不是「没日志」

- `log` 在 zsh 里被函数/别名遮蔽（报 `too many arguments`）。**必须用 `/usr/bin/log`**。
- 换绝对路径后：`/usr/bin/log show --last 1m` → **18,739 行**；`18:02:30–18:07:00` → **1,003,182 行**。
- ⚠️ 但本机 `log show` 的 `--start/--end` **解析不稳定**（同一批查询里出现互斥结果），故本文**只采用 `pmset -g log` 这一路自洽数据**，unified log 仅作交叉印证。

## 二、powerlog 侧（硬件级状态机）—— 只作旁证，且有污染

查 `PLSleepWakeAgent_EventForward_PowerState`（Event/State/KernelSleepDate）：

| 现象 | 实测 | 解读 |
|---|---|---|
| 最新记录 | **2026-10-09 15:36:10**（ID 40） | **18:03 那次睡眠在 powerlog 里根本没有** ⇒ 硬断电丢掉了未落盘的记录 |
| 唤醒事件的 `KernelSleepDate` | 多为 **0.0** | 内核侧没有记下有效的「入睡时刻」 |
| 异常行 ID 30 | `timestamp` 为**负数**（渲染成 1970-01-01）、`State = -1`、`KernelSleepDate = 0.0` | 睡眠状态机记到了**非法/零值入睡时刻** |
| 时间轴对齐 | powerlog 记 15:36:09 有 `Software Sleep`，但 `pmset` 当天**没有** 15:36 的睡眠 | powerlog 时间戳被本机**时钟跳变**污染（`rtcfx_exclude=0E-FF` / `-rtcfxdbg` 说明 RTC 本身在打补丁） |

⇒ powerlog 只能支持「睡眠状态机没有正常闭环」，**不能**拿来定 A/B。

## 三、为什么「唤不醒」这个方向更被支持

唤醒源只有四个：**电源键（EC 层）、开盖（EC 层）、RTC 闹钟（平台层）、AC 变化**。

- 电源键是 **EC 层**唤醒源，**不依赖 RTC**。现场实测：**按电源键毫无反应**。
- 预约 23 秒后的平台唤醒，**34 分钟不兑现**。

如果一个「真睡（S0ix）」的机器，EC 层电源键至少会把平台拉起来（哪怕是 DarkWake）。**两者同时失效 ⇒ 平台压根没到达「能被唤醒」的状态** ⇒ 更偏向 **假设 A「卡在入睡交接，没睡成」**，与 OC-Little 的官方定性一致。

⚠️ 保留一个反例余地：本机 RTC 正在打 `rtcfx` 补丁，若 **RTC 闹钟本身写不进去**，则「23 秒唤醒不触发」这条证据会被削弱。这正是需要物理判据兜底的原因。

## 四、判据与实验（用户现场执行）

### 4.1 零成本物理判据（下次实测时观察，最关键）

| 观察项 | 指向 **B（真睡、唤不醒）** | 指向 **A（没睡成、卡在交接）** |
|---|---|---|
| 机身温度 | **凉** | 发热 / 微温 |
| 风扇 | **停** | 转 / 有风（**主判据**） |
| HP 电源键 LED | ~~呼吸/闪烁~~ ⚠️ **不可用**：OC-Little 明说「AOAC 睡眠期间无呼吸灯闪烁」，灯不闪是**预期** | —— |
| 插拔电源线 | 有反应（唤醒） | 无反应 |
| 墙插功耗计（若有） | **1–3 W** | **10–20 W**（CPU 空转） |

> 有瓦特计的话这一项**单独就能定案**：真睡 = 个位数瓦，空转 = 十几瓦。
> 判据来源见 §七（社区交叉验证）：风扇/温度获多条独立来源支持；LED 因 AOAC 特性被降权。

### 4.2 90 秒决定性实验（二值结果，不受「我觉得」干扰）

```bash
# 1) 预约 2 分钟后的平台唤醒
sudo pmset schedule wake "$(date -v+2M '+%m/%d/%y %H:%M:%S')"

# 2) 手动入睡（苹果菜单 → 睡眠；或 sudo pmset sleepnow）

# 3) 之后 3 分钟什么都别碰
```

| 结果 | 判定 |
|---|---|
| 到点**自己亮屏回来** | 平台睡眠 + RTC 唤醒通路**都活着** ⇒ 问题只在「电源键/唤醒源接线」⇒ **真睡、唤不醒（B）** |
| 3 分钟后**依旧死寂** | 它**没走到能被唤醒的状态** ⇒ **卡在入睡转换、没睡成（A）** |

事后复核（重启后执行）：

```bash
/usr/bin/pmset -g log | grep -E "Entering Sleep|Wake from|DarkWake"
sudo pmset schedule cancelall      # 清理预约
```

⚠️ 若判据 4.1 显示「凉 + 风扇停」（像真睡）而 4.2 又不唤醒，则矛盾点落在 **RTC 闹钟未写入**（`rtcfx` 补丁嫌疑），此时应转去查 RTC。

## 五、与既有结论的关系

- 本文**不推翻**此前「AOAC 修复无效、指纹不变」的判定：18:03 那次的指纹与历史完全一致（睡前进、零 Wake、按键无响应、硬关机）。
- 本文**补上了**此前缺失的一环：把「睡死」拆成 **A/B 两态**，并给出**可定案的物理判据**，而不是继续在软件层反复猜。
- 与 `docs/sleep-fix-2026-10-09-aoac-wake-and-s3.md` 第七节线 20 引用的 OC-Little 原文一致：本类故障官方定性为「**始终没有睡眠成功**」，即 A。

## 七、社区交叉验证（2026-10-09 19:2x，用户问「看下社区确定一下」）

### 7.1 结论：社区给这类故障起了名字，而且**明确把本质定成 A（没睡着）**

**OC-Little《01-关于AOAC》原文（daliansky/OC-little，中文权威源）**：

> **睡眠失败** 主要表现为：睡眠后无法被唤醒，呈现死机状态，只能强制关机。
> **睡眠失败** 本质是**机器一直停滞在睡眠过程，始终没有睡眠成功**。

⇒ 社区不是把它归到「唤不醒」，而是**归到「没睡成」**（= 本文假设 **A**）。这篇报告 19:1x 的第三态结论，与社区官方定性**同一指向**。

### 7.2 硬前提：本机确实是 AOAC 机器（社区判据原话逐字命中）

OC-Little 给出的判据：「用 MaciASL 打开 `FACP.aml`，搜索 `Low Power S0 Idle`，如果 =1 即属于 AOAC 机器。」

本机实测（`docs/SysReport/ACPI/FACP-1.aml`，`iasl` 反编译）：

```
[070h 0112 004h]  Flags (decoded below) : 002384A5
                  Hardware Reduced (V5) : 0
                  Low Power S0 Idle (V5) : 1     ← 命中
```

⇒ **本机 = AOAC 机器**（成员级硬证据，非推断）。

### 7.3 社区把「睡死」拆成两类，本机落在第一类

| 社区类别 | 出处 | 现象 | 本质 | 本机 |
|---|---|---|---|---|
| **睡眠失败** | 《01-关于AOAC》 | 睡眠后无法唤醒、呈死机状态、**只能强制关机** | 一直停滞在睡眠过程，始终没有睡眠成功 | ✅ **逐条吻合** |
| **AOAC 唤醒不完整** | 《01-4-AOAC唤醒方法》 | 机器**已经进入了 S0 状态**，只是「不能点亮屏幕 / 不能更新电源数据」 | 唤醒了但恢复不完整 | ❌ 本机电源键**零反应**（不是「屏幕不亮但活着」）；且 `_PS0` 补丁**已装实测无效** |

`01-4` 原文那句「**这表明机器已经进入了 S0 状态**」是关键分水岭：社区认为「唤醒不完整」的前提是**机器已经活了**。本机按键毫无反应、无 LED 变化、无 RTC 兑现 ⇒ 不满足该前提。

### 7.4 社区给 AOAC 机器的「全套方案」，本机已基本走完

| 社区方案（《01-关于AOAC》AOAC解决方案） | 本机 | 证据 |
|---|---|---|
| 禁止 S3 睡眠 | ✅ | `ACPI/Patch#2` `_S3_`→`XS3_`（Enabled）+ `SSDT-NameS3-disable.aml`（Add#14）；全 ACPI 表里 `_S3_` **仅 1 处**，rename 精确命中 |
| 电源空闲管理（Deep Idle） | ✅ | `SSDT-DeepIdle.aml`（Add#11） |
| AOAC 唤醒补丁（`_PS0`/`_PS3`） | ✅ | `SSDT-PCI0.LPCB-Wake-AOAC.aml`（Add#12，10-09 已合并 `_PS0=\_WAK(0x03)`） |
| 关闭独显供电 | ✅ | `SSDT-dGPU-PowerOff-Darwin.aml`（Add#13） |
| NVMeFix（APST） | ✅ | `NVMeFix.kext` 在位 |
| 启用 ASPM / L1 | ⚠️ 挂空挡 | 实测 `pci-aspm-custom = 0`（从未写入链路寄存器） |

⇒ **「再补几个睡眠补丁」这条路已经走到头**：社区点名的补丁本机**全上了**，仍然睡死。这与社区自己的免责声明一致：

> **「AOAC 解决方案是临时解决方案。随着 AOAC 技术的广泛应用，可能将来会有更好的解决方法。」**

且社区明确指出 AOAC 路线下**两条常规睡眠补丁不适用**：

> 「AOAC 睡眠、唤醒和 S3 睡眠、唤醒不同，以下补丁**不在适用**：《PTSWAK综合扩展补丁》《PNP0C0E睡眠修正方法》」

⇒ 这**更正**了 09-29 那轮「本机缺 `PTSWAKTTS` 是高风险配置」的说法：那是拿 **S3 路线**的补丁表去套 **AOAC 路线**；AOAC 路线下它本来就不该出现。

### 7.5 必须修正的两条物理判据（§四 表要改）

**① 电源键 LED —— 降权，不可当判据。**
- HP 官方手册（ZBook Power G7）：正常睡眠时「front power light is **blinking**（indicating Sleep state）」。
- **但** OC-Little 明说：**「AOAC 睡眠期间无法正确显示工作状态，如睡眠期间无呼吸灯闪烁」**。
⇒ 在本机（仿制 AOAC 睡眠）下，**灯不闪是预期**，闪烁与否**没有区分度**。

**② 风扇 —— 升级为**主**判据。** 多条独立来源一致把「风扇还在转」当作「没真睡」的标志：
- 中文社区对「睡死」的标准描述：「屏幕不亮、**风扇持续运转**但系统无响应」（ask.csdn）；
- 开源项目 **Jamesits/S0ixEnabler**（强制开启 S0 Low Power Idle）把 **"Unable to wake up from sleep"、"Fan not stopping during sleep"、"Fan not spinning after wake up"** 直接列为已知副作用，并警告可能**过热**；
- Dell/Windows Modern Standby 侧：**合盖后仍温 = 仍在 S0**，S0 下可持续 20–50 W。

⇒ **风扇转/机身热 ⇒ A（没睡成，还在跑）；风扇停且凉 **且**唤不醒 ⇒ B（真睡、唤不醒）。**

**③ 一个已经发生过的本机实测 A 案例**：用户 09-28 晚合盖后「**没睡着，早上键盘很烫**」（见 `docs/sleep-wake-failure-2026-09-29.md` §十一）——这就是 A 的现场实测签名。

### 7.6 同门机型先例

- **HP ZBook 15 G3**（社区 EFI 仓库 `majohnst/EFI-HP-ZBook15G3`）README 直接把 `Sleep not working (better disable auto sleep)` 写进 Known issues —— HP ZBook 系弃疗睡眠的先例。
- **tonymacx86**（09-29 已记）：某 Honor 本合盖后「fans keep spinning, draining battery, impossible to wake」，与本机形态一致。
- **ArchWiki**：厂商已停止修 ACPI S3 的 bug，出厂向 Windows 的机器被鼓励用 Modern Standby；**若固件主动不报告 S3，多半是因为它本身有问题**。

### 7.7 本节结论

- 社区**认可**这类故障的存在并给了官方命名 **「睡眠失败」**，**本质定性 = A（没睡着、停滞在睡眠过程）**；本报告 19:1x 的第三态结论与之**同向**，可**升级为社区判据级**。
- 社区同时把它定性为 **AOAC 路线的固有短板 + 临时方案**，**无银弹**；本机已把社区点名的补丁全部上齐仍失败 ⇒ **继续加补丁的边际收益≈0**。
- 两条待厘清项（非结论）：
  1. 社区机制解释的前提是「AOAC 机器**进入 S3**」；本机已禁 S3（补丁 + rename 均已启用、命中精确），但**运行时是否真的对 macOS 隐藏了 S3 无法在 macOS 侧验证**（无 ACPI dump 能力）。若实际仍走了 S3，则社区机制可**直接解释**本机睡死。
  2. 社区说「禁 S3 ⇒ 机器将**不再睡眠**」；本机却在 18:02 仍被 `pmset` 记为 `Entering Sleep state` —— 这两点的落差值得作为**下一个取证方向**。
