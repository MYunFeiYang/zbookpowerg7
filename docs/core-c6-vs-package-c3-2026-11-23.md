## 1. 结论摘要

| 旧结论（十几轮沿用） | 新结论（本文件） | 把握度 |
|---|---|---|
| 睡眠期核停在 C3，`CC7:0%` = 核心没进 C6/C7 ⇒ 包卡 C3 的根因在核心侧 | **睡眠期 12 个线程 100% 全在 C6**（`CoreCState6Residency` 占 99.9%），`CC7:0%` 指的是 **Core C7**，不是 Core C6 | **>95%** |
| 包卡 C3 是"核心 C-state 不够深"导致 | 三条件中"核心 ≥C6"与"核显 RC6"均已满足，包仍停 C3 ⇒ 卡点是 PC3→PC6 的 **BCLK 关断 + VR 降压到 PSx** 这一层 | **~90%**（排除法） |

**一句话**：十几轮一直在找"核心为什么进不了 C6"，而核心**早就在 C6**。真正没达成的是包级 C6，它卡在 macOS 完全不参与的一层。

## 2. 决定性证据：Apple 官方每核 C-state 表

来源：`/var/db/powerlog/Library/BatteryLife/CurrentPowerlog.PLSQL`
表：`PLMacCPUGPUAgent_EventBackward_PerCoreCStatePStateResidency`
（只读打开，`mode=ro`；该表由 Apple powerlog 自己写入，与我的 MSR 读数完全独立）

### 2.1 原始值（按 12 行一批 = 12 个线程）

| 时间 | C3 | C6 | C7 | C10 | C6 占比 |
|---|---|---|---|---|---|
| 17:18:38 | 19,318 | 15,145,848 | 5,276 | 0 | 99.8% |
| 17:48:38 | 24,564 | 23,777,034 | 5,276 | 0 | 99.9% |
| **18:23:52（醒后）** | 26,720 | **43,509,360** | 5,276 | 0 | **99.9%** |

`C6 : C3` 的比例长期在 **600:1 ~ 1800:1**，C7 自开机以来只涨了 0（5,276 恒定），C10 恒为 0。

### 2.2 单位校准（这一步让它从"看起来像"变成"铁证"）

该表单位未在文档中标明，用睡眠跨度反推：

```
睡前参考点 17:48:38  C6 = 23,777,034
醒后参考点 18:23:52  C6 = 43,509,360
窗口 2114s（含 ~715s 清醒段 + 1399s 睡眠），ΔC6 = 19,732,326

纯清醒段实测速率       =  3,812 /s   （取 17:18:38→17:48:38 纯清醒窗口）
剔除清醒段贡献         = 19,732,326 − 715 × 3,812 = 17,006,626
纯睡眠段速率           = 17,006,626 / 1399 = 12,156 /s
```

**12 个线程 × 1000（毫秒/秒）= 12,000/s** ⇒ 实测 **12,156/s = 101.3%**。

101.3% 的 +1.3% 来自清醒参考速率取样窗口不精确（±2% 级），物理上不可能超 100%（每线程每秒最多累积 1000ms）。

⇒ **单位 = 毫秒/线程/秒；睡眠期 12 线程 C6 驻留 = 100%，一个线程都没漏。**

同理清醒段 3,812/12,000 = **31.8%** 线程在 C6 —— 与"平时有 1~3.65 核在跑"（见 §117）完全吻合。

## 3. 误读的根因：`CC7` 到底指什么

`sysctl machdep.xcpm.deep_idle_last_stats` 输出：

```
0:22:21 CC7:0% C2:0% C3:99% C6:0% C7:0% C8:0% C9:0% C10:0%
         ^^^^^^ Core C7        ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ Package C2/C3/C6/C7/C8/C9/C10
```

- **`CC7` = Core C7**，前缀是 `C`（Core）不是 `P`。
- **这个接口根本不报告 Core C6**。它只报 Core C7 一个核心级字段，其余全是包级。
- 十几轮把 `CC7:0%` 读成"核心连 C6/C7 都没到"，是把 **Core C7** 当成了 **Core C6**，再把"某一个核心级字段为 0"升级成"所有核心级状态都没达成"。

> 为什么这条路一直没被证伪：`CC7:0%` 每次采样都稳定复现（因为核心确实不进 C7），看起来像"铁一样的观测"，反而掩盖了它只是**一个特定字段**而非"核心整体状态"。

**教训（方法学）**：字段名不能靠"看起来像"解读。`CC7` 的第二个 `C` 是 Core、`C3/C6/C7` 那个 `C` 是 package —— 同一行里两个 `C` 含义不同，这种缩写必须查一手定义再下结论。本机 `deep_idle` 的实现（X86PlatformShim）不暴露 Core C6，所以**任何"核心没进 C6"的判断在这个接口上都不可能成立**，只能靠 powerlog 或直接读 MSR。

## 4. 卡点重定位：Intel 三条件排除法

Intel 官方 Package C-State 准入（edc.intel.com，一手）：

- **PKG C3** = 所有 IA 核 ≥C6 **+** 核显 RC6 **+** 平台 LTR 许可
- **PKG C6** = PKG C3 **+ BCLK 关断 + IMVP VR 降压到 PSx**

逐条核销本机状态：

| 条件 | 本机状态 | 依据 | 把握度 |
|---|---|---|---|
| 所有 IA 核 ≥C6 | ✅ **100% 在 C6** | powerlog per-core 表，单位已校准（§2） | >95% |
| 核显 RC6 | ✅ 睡眠期 PP1 = **0.008W** | 首次 RAPL 睡眠分解 | >95% |
| 平台 LTR 许可 | ✅ 已全 ignore（`debug.pmcdump.ltr_ignore=8280` / 0x7FFFFF） | PMCDump 实测 | >90% |
| **BCLK 关断 + VR 降压到 PSx** | ❓ **唯一未满足项** | 排除法 | ~90% |
| 包级实际状态 | 停 C3（`C3:99%`，`PKG C6/C7/C10 = 0`） | deep_idle + RAPL 双证 | >95% |

**结论：卡点在 BCLK 关断 + IMVP VR 降压。** 这两件事由 PCU 通过 SVID/IMVP 协议直接与主板 VR 控制器协商，路径上没有任何 macOS 驱动参与 —— 与"MCHBAR+0x5D30 ILTR Override"（XCPM 可控）不是同一层。

顺带修正 §68 的旧论断：睡眠期 MBD=0、ILTR override 已被清零（§38 实测），所以"override 在 LTR_IGNORE 之上压制"这个根因本来就不成立 —— 它现在更不重要了，因为**真正的门压根不在 LTR 这一支**。

## 5. 3.6W 归因修正（VR 损耗此前被漏算）

首次 RAPL 分解给出睡眠期 CPU 封装 **2.06W**，对照整机电池侧 3.6W，"非 CPU = 1.54W"。这个减法**不严谨**：封装功耗是 VR 的**输出**，而电池看到的是 VR 的**输入**。

```
CPU VR 效率取 87%（CML-H 移动 VR 典型 85~90%）
封装 2.06W ÷ 0.87 = 2.37W  ← 电池侧为 CPU 供电实际支出
VR 损耗 = 0.31W
真正"非 CPU" = 3.6 − 2.37 = 1.23W
```

修正后的 3.6W 构成（把握度 ~80%，VR 效率为典型值非本机实测）：

| 项目 | 功率 | 占比 |
|---|---|---|
| CPU 封装（core C6 1.12 + DDR 0.57 + uncore 0.36 + GT 0.008） | 2.06W | 57% |
| CPU VR 转换损耗 | ~0.31W | 9% |
| 平台其余（PCH / SSD / 屏关态 / EC / 电池 DC-DC / 待机轨） | ~1.23W | 34% |

**含义**：即便包级 C6 完全达成，core 也最多从 1.12W 降到 ~0.6W、uncore 略降，整机仍在 **2.8~3.0W**。剩下那 1.2W 平台开销与 C-state 无关，任何 CPU 侧努力都动不了它。

## 6. 未解项（明确列出，不装作已解决）

1. **为什么 PC3 进不了 PC6 的具体信号**（<80%）—— 需要读 PCU 侧 BCLK/VR 状态，macOS 无接口；Linux `pmc_core` 的 `dmi_l1_status`/`pkg_cstate_limit` 是同类信息，本机无 Linux 侧取证。
2. **Core 为何不进 C7**（<80%）—— 但 CML 上 Core C6 已含 core 级 VR 降压，C7 只是多一层 L2 flush，对功耗贡献小；且 C7=0 与"包卡 C3"无因果关系（包 C3 只要求 ≥C6）。
3. **长睡期间的周期性唤醒污染**（已量化，影响小）—— `pmset -g sched` 显示 `CSPNEvaluation` 每 ~7229s（2h）排一次、`calaccessd.travelEngine.periodicRefreshTimer` 定点排多次。按每次 DarkWake 10~30s @12W 估算，8h 内 4 次 ≈ 960~1440J，占 8h 总能耗（~104kJ）的 1~1.4%。**不值得动手**，但引用历史 3.6W 时应知道它含这部分。

## 7. 这对"还能不能优化"的意义

- **CPU 侧已到底**：核 C6 100%、核显 RC6、LTR 全 ignore —— 三个软件可影响的变量全部处在最深可用值。
- **剩余可争取的只有 0.56~0.79W**（包进 C6），且入口在固件/VR 层，macOS 够不到。
- **真正的大头变成 1.23W 平台开销**，它不随 C-state 变化。要动它只能关设备（SSD/屏/雷电/USB 供电），而睡眠期这些通常已在 D3/PS4，边际收益同样有限。

⇒ 3.6W 作为"本机在当前固件 + macOS 组合下的地板"这个判断**不变**，但**理由彻底换了**：不是"核心不够深"，而是"核心已经最深、包级那一跳由固件把着"。

## 8. 复算方法（可重现）

```sql
-- 每核 C-state（需只读打开 powerlog）
SELECT ID, timestamp, CoreId, AveragePStateFrequency,
       CoreCState3Residency, CoreCState6Residency, CoreCState7Residency,
       CoreCState8Residency, CoreCState9Residency, CoreCState10Residency
FROM PLMacCPUGPUAgent_EventBackward_PerCoreCStatePStateResidency
ORDER BY ID;   -- 每 12 行 = 一个时间点的 12 个线程
```

判定规则：
- 每批 12 行求和，`C6 / (C2+C3+C6+C7+C8+C9+C10)` > 95% ⇒ 核心已在 C6
- 睡眠段速率校准：`(ΔC6 − 清醒段秒数 × 清醒速率) / 睡眠秒数`，理论上限 `12,000/s`（12 线程 × 1000ms）
- 实测 12,156/s ⇒ 100% 线程 C6
