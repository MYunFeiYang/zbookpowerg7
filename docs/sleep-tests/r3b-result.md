## 3. 副产物①：又一次 RTC/CMOS 被写坏（时钟 → 2019-01-01）

两条独立来源指向同一个"错误时刻"：

| 来源 | 值 | 说明 |
|---|---|---|
| `stat /var/vm/sleepimage` | mtime = **2019-01-01 08:01:05** | 17:19 那次 boot 时它是 17:19（会随 boot 变化）⇒ 说明**被某次 boot 重建** |
| `log show` 输出（§[5] 窗口内） | **70 行**条目时间戳 = `2019-01-01 08:00:44` | log 数据库里**存在一个时钟 ≈ 2019-01-01 08:00:44 的 boot session** |

⇒ 差值 21 s = "boot 后创建 sleepimage 占位"的典型间隔。
⇒ **与既有结论一致**：四层 RTC 防护全开，macOS 自己仍会写坏 CMOS（`AppleRTC` 休眠密钥 `0x80–0xAB` 落在 HP 校验和区）。

### 3.1 ✅ 已坐实（09-21 10:20 用户确认 ＋ 本轮补取新证据）

**用户确认：BIOS 报 POST 005。** 加上本轮补取的一条**直接解码**证据，此条从"推断"升为**实锤**：

| # | 来源 | 值 | 取证方式 |
|---|---|---|---|
| **1 ★** | `/var/run/utmpx` 原始字节 **offset 928** | **int64 = `1546300844`** = `2019-01-01 00:00:44 UTC` = **本地 2019-01-01 08:00:44** | 本轮 python 直接解二进制（`struct.unpack('<q')`） |
| 2 | `who -b` | `system boot  Jan  1 08:00` | 本轮 |
| 3 | `log show` §[5] 窗口 | **70 行**时间戳 = `2019-01-01 08:00:44` | 上次取证 |
| **3b ★★** | `verdict2` §[C]/§[D]：**一整段内核 boot trace** | 以 `2019-01-01 08:00:44.000294` 起头：`mem_actual` → `PMAP: PCID enabled` → **`Darwin Kernel Version 25.6.0`** → `vm_page_bootstrap` → `ACPI: sleep states S0 S3 S4 S5`（该窗口 1,104,149 行） | 上次取证（该段随本轮一并入库） |
| 4 | `stat /var/vm/sleepimage` | mtime = **2019-01-01 08:01:05** | 上次取证 |

⇒ **#3b 是"时钟被写坏"最直观的一张图**：这不是"某几行时间戳异常"，而是**整整一次启动的全部内核日志都落在 2019-01-01 08:00:44 之后**（`Darwin Kernel Version` 那行就是内核第一条自报版本）。

**★ 为什么证据 #1 能定位到"就是今早这次启动"（关键推理）**：
`/var/run/utmpx` 是**开机即重建的易失库**，其内容**只属于当前这次 boot session**。而它里面同时躺着：
- `boot  Jan 1 08:00`（← 就是我们解出来的那条 2019 记录）
- `<账户名> console Sep 21 08:53`（← 今天早上的登录；原文含真实账户名，公开仓库已脱敏）

⇒ **那条错误的 boot 记录只可能属于今天这次启动**，不可能是 09-20 的残留。
⇒ **今早 08:52:54 开机时，系统从 RTC 读到的时间就是 `2019-01-01 08:00:44`**，约 40 s 后被 NTP 校正（`console` 登录落在 08:53）。
⇒ **这正是用户看到的那个 POST 005。**

**★ 写坏是哪一次睡眠造成的？（本轮新增判定）**

| 睡眠 | 是否写坏 RTC | 依据 | 级 |
|---|---|---|---|
| **21:03:35 合盖那次** | ✅ **确凿** | 它之后到 08:52 之间**没有任何一次启动** ⇒ RTC 内容原样留到今早 ⇒ 今早读到的 2019 只可能来自它 | 🟢 |
| 19:02:41 第一次（脚本触发） | ⚠️ **未写坏**（倾向） | 随后 19:08 那次启动的 `console` 记录落在 **19:08**（不是 2019）⇒ loginwindow 落这条记录时读到的时钟是对的 | 🟡 单条推断 |

⇒ 也就是说：**R3b 这一轮只写坏了 1 次 RTC**，而**恰恰是"本不该发生"的那一次** —— 21:03 的合盖睡眠之所以会睡下去，**正因为看门狗失效、`standbydelay` 没被回滚**（§4）。
⇒ ⚠️ **这条把工程教训钉得更死**：「自动回滚没执行」的代价不只是"配置裸奔一夜"，而是**实实在在多写坏了一次 CMOS、多了一次 POST 005**。
⇒ 记数：**这是第 4 次 POST 005**（09-16 六次尝试中 3 次 ＋ R3b 1 次）。

⚠️ **一处未解释的旁支（不影响结论，仅备案）**：`last reboot` 里**没有今天这次启动的记录**（最新只到 09-20 20:04），`last` 里也 grep 不到任何 2019 记录。即 **wtmp 没有收到今天这条 BOOT 记录**，而 utmpx 收到了。两者不一致的原因未查明 ⇒ **判据一律以 utmpx 原始字节为准，不用 wtmp。**

## 4. 副产物②：看门狗（自动兜底）**完全失效** —— 这是本轮最重要的工程教训

| 检查项 | 结果 | 说明 |
|---|---|---|
| `MARKER` | 仍是 `ARMED 2026-09-20 19:01:12` | 未写 `DONE` / `BOOT-ROLLBACK` |
| `.armed` | **仍在** | `CLEANUP()` 会删它 ⇒ 说明 CLEANUP **没跑过** |
| `/var/log/watch.log` | **不存在** | watch.sh 第 13 行的冷启动回退路径（`OUT=/var/log`）**从未被走到** |
| `/Library/LaunchDaemons/com.wb.r3b.watch.plist` | **不存在** | 但 `.armed` 还在 ⇒ **不是自己的 CLEANUP 删的** |
| `wb-r3b-watch.out/.err` | 存在、0 字节、mtime 19:01:08 | launchd 起过 job，脚本自己重定向走了 |

**最可能的凶手**：`/Library/LaunchDaemons/` 目录 mtime = **20:13**，同时 `com.sangfor.aTrustDaemon.plist` = 20:13、`com.sangfor.eaio.service.plist` / `com.sangfor.saio.appwatch.plist` = **20:06**；19:56 有 `system_installd` 诊断报告 ⇒ **公司安全软件 aTrust（深信服）在 19:56–20:13 之间做了自我更新/重装，期间清掉了我们的 plist**（多家安全软件会接管/清理 LaunchDaemons）。

**结论（工程纪律，下次必守）**：
1. 🔴 **不要把"自动回滚"托付给 `/Library/LaunchDaemons` 的自建守护** —— 会被第三方安全软件清理，且失效时**无声**。
2. 🔴 **更根本的**：这次失效的**不是回滚逻辑，而是"机器根本没走到正常唤醒"** —— 冷启动回滚路径依赖 `RunAtLoad`，而 plist 已被删 ⇒ 两条腿都断。
3. ✅ **改用**：① 测试窗口内**人在旁边**，测完立刻手工回滚；② 或把回滚做成 `pmset` 之外的"可自证"形态（例如写入一个开机就报的 `~/Desktop/请回滚.txt` + `osascript` 弹窗），而不是静默守护。

## 6. 对 S4 这件事的净影响

- **★ 代价模型已从"概率"变"既定"**（09-21 10:20 确认后）：**武装休眠 ⇒ RTC 被写坏 + POST 005，现在 4/4**（09-16 六次尝试里 3 次 ＋ R3b 1 次）。⇒ 今后任何"真休眠 / 写 RTC"的实验，都必须**按"会重置 CMOS、时钟回 2019、开机要按 F1"来定价**，不能再写成"有概率"。好消息：**议程剩下的 ②③④ 全都不碰 RTC**，这一点上无额外风险。
- **议程 ① 关闭**：`hbfx-ahbm` + `standbydelay 0` 这条路**实测走不通**，而且代价比 R3 更高（R3 是软失败=正常唤醒；R3b 是硬失败=强制断电 + 写坏时钟）。
- **`hbfx-ahbm` 这条从未测过的路径，现在测过了 ⇒ 判不通行**。
- **"在已试过的配置空间里没解"这句，现在覆盖到了最大**（R3 软失败 + R3b 硬失败 + 09-16 五次 mode 25 失败）。
- ⚠️ **仍未闭环的一点**：R3b 的内核轨迹**整段丢失**（`sleep params` 0 命中）⇒ 无法确证"是否真的走到 `type 4`"。但**行为证据（内核停摆 + 未写镜像 + 需强制断电）已足以判"这条路不能用"**，且这正是议程预写的失败形态。
- **剩余可测**（见 `next-test-agenda.md`）：② OC 日志核 `DevirtualiseMmio`（低风险，与"S4 能不能用"关系弱）｜③ Win 功耗量准（独立价值）｜④ `dmpstore`（顺手，门后是死 S3）。
